# 입찰 실적 기록

우리가 낸 권장가와 **실제로 벌어진 일**을 대조해 오차를 남긴다.

## 왜 필요한가

`auction-bid-price` 는 *"입찰 후 실제 낙찰가·응찰자수·2순위 금액을 물어 기록한다"* 고
적어놓았지만 **기록할 곳이 없었다.**

지금 계수는 시장 전체 데이터(지지옥션·대법원·온비드)를 따라간다.
그런데 **우리 판단이 얼마나 빗나갔는지는 어디에도 측정되지 않는다.**

- 시장 낙찰가율이 78% 라는 것과, **우리가 78% 를 맞혔는가**는 다른 문제다
- 이 시스템은 **1,346,670원(1.7%) 차이로 2순위 패찰한 사건**을 계기로 만들어졌다.
  그런 사건이 몇 건 더 있었는지 지금은 셀 수 없다

**10건이 쌓이면 예측 로직을 실측으로 보정한다.**

## ★ 2순위 금액에 대하여 — 2026-08-14 정정

**이전 판에 "2순위 금액은 어느 DB에도 없다. 현장에서 개찰을 본 사람만 안다"고 적혀 있었다. 사실이 아니다.**

지지옥션 **상세 페이지에 순위별 응찰금액이 공개된다.** 2026-08-14 실물 3건 전부에서
2순위가 확인됐고, 그중 1건은 3순위까지 나왔다.

다만 **쉽게 얻을 수는 없다.**

| 경로 | 2순위 |
|---|---|
| 지지옥션 **목록 검색·CSV** (`ggi-collect` 가 긁는 것) | **없음** |
| 지지옥션 **상세 페이지** | **있음** — 단 인쇄 전용 CSS 라 화면 innerText 로는 안 잡힌다 |
| 대법원 API (`sale_result`) | 없음 |
| 온비드 API (`bidresult`) | 없음 |

→ **물건마다 상세를 열어야 하므로 대량 수집은 비효율이다.**
전량(주당 수백 건)을 긁으려면 토큰을 300초마다 재발급하며 페이지를 열어야 한다. 비용만 크다.

### 그래서 이렇게 확보한다

| 대상 | 방법 |
|---|---|
| **우리가 입찰한 건** | 현장에서 직접 확인. 이건 빠뜨리지 않는다 |
| **그 외** | `ggi-interest-npl-scan` 이 관심 물건 상세를 열 때 함께 기록 |
| 목표량 | **월 20~30건이면 충분** |

**왜 전량이 필요 없는가** — 승률곡선(`bid-win-curve`)은 **낙찰가와 유찰 분포**로 만든다.
그건 목록 데이터만으로 이미 확보돼 있다(30% 저감 2회 유찰 1,036건).
2순위는 곡선을 **만드는** 재료가 아니라 곡선이 맞는지 **검증하는** 재료다. 검증에는 수십 건이면 된다.

폴더가 없으면 만든다. **기존 항목은 절대 덮어쓰지 않는다. append 만 한다.**

## STEP 1 — 무엇을 물을 것인가

사용자가 결과를 알려주면, **빠진 것만 골라서** 묻는다. 이미 준 정보를 다시 묻지 않는다.

### 반드시 확보할 것

| 항목 | 왜 필요한가 |
|---|---|
| **사건번호 · 법원** | 저감률 판정과 물건 식별 |
| **결과** | 낙찰 / 패찰 / 미입찰(포기) / 유찰(아무도 안 들어옴) |
| **우리 입찰가** | 실제로 써낸 금액. 권장가와 다르면 그 이유도 |
| **실제 낙찰가** | 패찰이면 1순위 금액 |
| **응찰자수** | 경쟁강도 실측 |
| **★ 2순위 금액** | **가장 중요.** 우리가 낙찰이면 2순위가 얼마였나, 패찰이면 우리가 몇 순위였나 |

### 있으면 좋은 것

- 개찰 전 지지옥션 조회수 (경쟁강도 사전 예측의 정확도 측정)
- 현장에서 느낀 것 (특정 응찰자가 여러 물건에 들어왔다, 대리인이 많았다 등)
- 미입찰이면 **왜 포기했는지** — 이게 다음 판단의 재료다

**모르는 값은 `null` 로 둔다. 추정치를 넣지 않는다.**
"아마 2~3명쯤"은 기록하지 않는다. 그런 값이 섞이면 오차 통계가 무의미해진다.

## STEP 2 — 우리 예측을 찾아온다

`계수변경이력/계수변경로그.md` 나 이전 대화에 그 물건의 권장가 산출 기록이 있으면 가져온다.
없으면 사용자에게 묻는다: *"이 물건에 우리가 얼마를 권했었나요?"*

**권장가가 없으면 오차를 낼 수 없다.** 그 경우 `예측` 을 `null` 로 두고
"시장 데이터"로만 기록한다. 그래도 응찰자수·2순위는 값어치가 있다.

`bid-win-curve` 를 함께 돌렸다면 **양쪽 값을 모두** 기록한다.

### 필드 규칙

- **금액은 원 단위 정수.** 콤마·억·만 축약 금지 (JSON 이므로 숫자 그대로)
- `결과` 는 `낙찰` / `패찰` / `미입찰` / `유찰` 넷 중 하나
- `우리순위` 는 패찰일 때만. 낙찰이면 `1`
- **`경쟁최고가`** — 우리가 낙찰이면 2순위 금액, 패찰이면 1순위 금액.
  **어느 쪽이든 "우리가 이기려면 넘어야 했던 금액"이다.** 승률곡선 검증의 핵심 값이다
- **모르는 값은 `null`.** 빈 문자열이나 0 으로 채우지 않는다
- **채무자·임차인 실명, 주민번호, 계좌번호는 기록하지 않는다.** 필요하면 `A씨` 로 쓴다

## STEP 4 — 오차 계산

| 지표 | 계산 |
|---|---|
| 권장가 대 낙찰가 | `낙찰가 - 권장가` (양수 = 우리가 낮게 봤다) |
| 낙찰가율 오차 | `실제 낙찰가/감정가 - 예측 낙찰가율` (%p) |
| 응찰자 오차 | `실제 - 예측` (명) |
| 밴드 적중 | 실제 낙찰가가 `[밴드하단, 밴드상단]` 안인가 |
| **이기려면 필요했던 금액** | `경쟁최고가 + 1원` |

**패찰했는데 밴드 안에 낙찰가가 있었다면** — 계수는 맞았고 **우리가 밴드 하단을 쓴 것**이다.
이건 계수 문제가 아니라 의사결정 문제다. 구분해서 기록한다.

### ★ 「져도 되는 패찰」을 구분한다 — 2026-08-14 신설

**패찰이 전부 실패는 아니다.** `bid-win-curve` 로 확인한다.

```
이기는 데 필요했던 가격의 기대이익  <  최적가의 기대이익   →   져도 되는 패찰
```

실측 예 — 2025타경102188(20% 저감 2회 유찰, V=96.7%). 경쟁최고가가 71.00% 였다.
최적가 68.25% 의 기대이익이 17.21, 이기는 데 필요한 71.25% 의 기대이익이 15.61.
**이기려면 감정가의 1.60%(7,296,000원)를 버려야 했다. 패찰이 옳았다.**

→ `배운점` 에 "졌지만 기대이익 기준으로는 맞았다"를 명시한다.
**져서 아쉬운 것과 잘못 판단한 것을 흐리면 다음 건에서 과다 입찰한다.**

## 10건이 쌓이면

`coefficient-auto-update` 에 **보정 근거**로 넘긴다. 단, 주의할 것이 있다.

**우리 실적은 표본이 극히 작고 편향돼 있다.**
우리가 입찰한 물건은 우리가 고른 물건이다. 시장 전체의 대표 표본이 아니다.

따라서 **계수를 직접 교체하지 않는다.** 대신 이렇게 쓴다.

| 우리 실적이 말하는 것 | 어떻게 쓰는가 |
|---|---|
| 밴드 적중률이 낮다 | 계수가 아니라 **밴드 폭**을 넓혀야 한다 |
| 낙찰가율을 계속 낮게 본다 | 특정 저감률·회차·용도군에 **체계적 편향**이 있는지 시장 데이터로 재확인 |
| 응찰자를 계속 적게 본다 | **조회수 밴드**를 재산출한다 |
| 아깝게 진 건이 반복된다 | **`bid-win-curve` 로 「져도 되는 패찰」이었는지 먼저 판정**한다. 옳은 패찰이면 고칠 것이 없다 |
| 승률곡선 예측과 실제가 어긋난다 | 곡선의 표본 기간·셀 범위를 재검토한다 |

**"우리가 3건 졌으니 계수를 올리자"는 하지 않는다.** 3건은 우연으로 설명된다.

## 미입찰 기록의 가치

포기한 물건도 기록한다. 나중에 그 물건이 얼마에 팔렸는지 보면
**"안 들어간 게 옳았나"** 를 판단할 수 있다.

포기 사유는 구조화해 남긴다:
`권리 위험` / `명도 위험` / `가격 안 맞음` / `자금 사정` / `현장 확인 결과` / `기타`

같은 사유로 반복해서 포기한다면, 그 조건을 **사전 스크리닝**에 넣을 수 있다.

## 연계

- `auction-bid-price` — 권장가를 낸 스킬. 이 기록이 그 스킬의 정확도를 측정한다
- `bid-win-curve` — 승률곡선. `경쟁최고가` 가 이 스킬의 유일한 검증 데이터다
- `ggi-interest-npl-scan` — 관심 물건 상세를 열 때 2순위를 함께 기록한다
- `coefficient-auto-update` — 10건 이상 누적 시 보정 논의
- `pipeline-health-check` — 실적 기록이 멈췄는지도 함께 본다
- `00_시장데이터/계수변경이력/계수변경로그.md` — 그 시점에 어떤 계수를 썼는지 확인
