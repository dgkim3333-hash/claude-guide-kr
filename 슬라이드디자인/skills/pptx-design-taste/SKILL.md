# pptx-design-taste — 슬라이드 모드 우선순위 규약

> `design-taste-frontend`(안티슬롭 프론트엔드 스킬)를 PPTX 덱 제작에 쓸 때 **먼저** 적용하는 한 장짜리 규약.
> 원본 스킬을 대체하지 않는다. 원본의 **결정 권한만 회수**하고 **판정 능력은 그대로 살린다**.

---

## 0. 왜 이 규약이 필요한가

`design-taste-frontend`는 **디자인이 아직 정해지지 않은 상태**를 전제로 만들어졌다. 브리프를 읽고 폰트·컬러·레이아웃을 매번 새로 고르며, 페이지마다 배치가 반복되는 것을 결함으로 취급한다(`DESIGN_VARIANCE 8`, §4.3, §9).

슬라이드 덱은 정반대 전제다. 폰트·컬러·존 좌표가 **이미 확정**되어 있고, 페이지마다 동일해야 한다.

두 문서가 부딪히는 지점은 **"누가 정하느냐" 하나뿐**이다. 그 밖의 영역(촌스러움 판정, 밀도, 카피 검수)에서는 방향이 같다. 따라서 이 규약은 결정 권한만 정리하고, 나머지는 원본을 그대로 흘려보낸다.

---

## 1. 발동 조건

산출물이 다음 중 하나면 슬라이드 모드로 전환한다.

- `.pptx` / `.potx` 파일
- 16:9 슬라이드 덱, 발표자료, 물건카드, 제안서 덱
- "슬라이드로 먼저 HTML 시안" 요청

웹페이지·랜딩페이지·포트폴리오는 **이 규약 대상이 아니다**. 그 경우 `design-taste-frontend`를 단독으로 쓴다.

### 1.A 자가 감지 — 원본이 먼저 걸린 경우

`design-taste-frontend`가 먼저 호출됐더라도, 다음 중 하나에 해당하면 **즉시 이 규약으로 갈아탄다**. 원본의 브리프 추론·다이얼 설정을 진행하기 전에 전환한다.

- 산출물이 `.pptx` / 슬라이드 덱 / 발표자료다
- 사용자가 스킬 이름을 직접 부르며 PPT·슬라이드 작업을 요청했다
- "촌스럽다 / 디자인 감각 / 안티슬롭 / AI 티 난다"로 시작했지만 대상이 슬라이드다

전환했으면 그 사실을 한 줄로 알린다.

> 슬라이드 덱이므로 `pptx-design-taste` 규약으로 전환합니다.

### 1.B 원본 로드 (필수 절차)

이 문서는 **원본의 요약본이 아니다.** §4가 나열하는 안티슬롭 항목은 발췌이며, **정본은 원본 `design-taste-frontend`의 본문**이다.

따라서 슬라이드 모드에 들어가면 **반드시 `design-taste-frontend`를 함께 로드해 §9(AI Tells)·§4.9(밀도)·§4.8(이미지 전략) 원문을 읽는다.** 원문 항목이 이 문서의 발췌보다 많으면 **원문을 따른다**.

원본을 로드하지 못했으면 그 사실을 밝히고, 이 문서의 발췌 범위에서만 판정했다고 명시한다.

### 1.C 선언

발동하면 답변 첫 줄에 다음을 선언한다.

> **슬라이드 모드** — 덱 규격 `<규격명>` 적용. 폰트·컬러·좌표는 규격 고정, 안티슬롭 판정만 스킬 적용. (원본 로드: 완료 / 실패)

## 2. 최상위 조항 — 결정 권한의 분리

**덱 규격(프로젝트 지침·템플릿·브랜드 매뉴얼)이 정한 값은 이 스킬과 원본 스킬의 모든 미학 규칙보다 상위다. 충돌하면 스킬이 진다.**

> 이 저장소에서 **덱 규격 = `design-system.md`**, **브랜드 값 = `brand.config.md`** 다.
> 아래 표의 「규격 지정」은 전부 그 두 파일을 가리킨다.

### 2.A 스킬이 **고르지 못하는** 것 (규격이 이미 정함)

| 항목 | 원본 스킬 | 슬라이드 모드 |
|---|---|---|
| 서체 | §4.1 브리프 따라 선택 | **규격 지정 서체 고정.** 대체·혼용·폴백 금지 |
| 액센트 컬러 | §4.2 자유 선택 | **규격 지정 컬러 고정** |
| 레이아웃 변주 | §4.3 + `DESIGN_VARIANCE 8` | **존 좌표 고정.** 변주는 본문 박스 *안에서만* |
| 다크/라이트 | §8 다크모드 필수 | **규격 배경 고정** (통상 흰 배경) |
| 모서리 반경 | §4.4 자유 | 규격 반경 스케일 |
| 그림자 | §4.4 자유 | 규격 섀도 라이브러리 |
| 그라디언트 | 브리프 판단 | 규격이 각도·스톱·개수 상한을 정했으면 그대로 |

규격에 없는 값만 스킬이 고른다. 있으면 그대로 쓴다.

### 2.B 원본 §13 OUT OF SCOPE 예외 해제

원본은 "대시보드 / 데이터 테이블 / 밀집 제품 UI"를 범위 밖으로 밀어낸다. 슬라이드는 **KPI 타일·차트·비교표가 본체**다. 슬라이드 모드에서 이 배제 조항은 **해제**한다.

단 밀도 규율(원본 §4.9)은 살린다 — 20행 표, 근거 없는 소수점 정밀도, 25단어 넘는 하위 문단은 여전히 금지.

### 2.C 웹 전용 항목 — 슬라이드에서 N/A

다음은 슬라이드에 존재하지 않는 개념이다. 프리플라이트에서 **평가하지 않는다**.

- Core Web Vitals (LCP / INP / CLS), DOM 비용
- 다크모드 토큰·양쪽 모드 테스트
- `prefers-reduced-motion`, 하드웨어 가속, `will-change`
- 반응형 붕괴, 모바일 `px-4`, `min-h-[100dvh]`
- `useEffect` 정리 함수, `'use client'` 격리, 메모이제이션
- 스크롤 애니메이션 일체(§5 스티키 스택 / 호리즌탈 팬 / 스크롤 리빌), `ScrollTrigger`, `useScroll()`
- 호버·포커스·액티브 상태(§4.5) — 인쇄물에는 상태가 없다
- 폼 컨트라스트, CTA 줄바꿈, 내비게이션 높이

## 3. 다이얼 재정의

원본 §1의 세 다이얼을 슬라이드용으로 다시 잡는다.

```
DESIGN_VARIANCE : 3   (프레임) / 6 (본문 박스 내부)
MOTION_INTENSITY: 0
VISUAL_DENSITY  : 5-6
```

- **`DESIGN_VARIANCE` 이중값** — 헤더·제목·부제·본문박스·푸터의 다섯 존 좌표는 전 슬라이드 동일(값 3에 해당). 본문 박스 *내부* 구성은 슬라이드마다 달라야 한다(값 6). 8장 연속 같은 본문 패턴은 원본 §9의 "섹션 레이아웃 반복" 위반으로 똑같이 잡는다.
- **`MOTION_INTENSITY 0`** — PPTX는 정지 화면으로 읽힌다. 화면 전환·개체 애니메이션은 규격이 명시적으로 요구할 때만. 원본의 "모션을 주장했으면 실제로 움직여야 한다" 조항은 적용하지 않는다.
- **`VISUAL_DENSITY` 상향** — 웹 랜딩(3-4)보다 높다. 슬라이드 본문 박스 하단이 비면 결함이다. 다만 밀도를 채우려고 존 경계를 침범하는 것은 더 큰 결함이다(§5 참조).

## 4. 살려 쓰는 것 — 원본에서 그대로 가져오는 자산

> **아래는 발췌다. 정본은 원본 본문이며, §1.B에 따라 반드시 원문을 읽고 그쪽을 따른다.**

**§0.D 안티 디폴트**
AI 보라색 그라디언트, 다크 메시 위 가운데 정렬 히어로, 똑같은 카드 3개, 전면 글래스모피즘 — 슬라이드에서도 그대로 촌스럽다.

**§9 AI Tells (핵심 자산 — 원문 전체가 정본)**
- 가짜 스크린샷을 도형으로 흉내내기 → 금지. 자리표시를 넣고 알린다
- 손으로 그린 장식 SVG → 금지
- `Jane Doe` / `Acme Corp` 류 가짜 데이터 → 금지
- 장식용 점(dot), 의미 없는 상태 표시등 → 금지
- 섹션 번호 eyebrow(`001 · 개요`, `00 / INDEX`) → 금지
- 버전 푸터(`v1.4.2`, `Build 0048`) → 금지
- 히어로 하단 장식 텍스트 스트립 → 금지
- 이미지 위에 겹친 알약 라벨 → 금지
- 채워진 트랙이 있는 점수 막대를 비교 시각물로 쓰기 → 금지
- 근거 없는 도시명·시각·날씨 스트립 → 금지
- 사진 크레딧을 장식으로 다는 캡션 → 금지
- 제목 옆에 떠 있는 우상단 부연 텍스트 → 금지
- 긴 목록 전 행에 위아래 테두리 → 금지

**§4.9 콘텐츠 밀도**
5개 넘는 항목을 밋밋한 목록으로 늘어놓지 않는다. 표·타일·차트 중 맞는 형태를 고른다.

**§4.8 실제 이미지 원칙**
도형으로 스크린샷·차트를 흉내내지 않는다. 진짜 데이터로 진짜 차트를 그리거나, 자리표시를 남기고 사용자에게 알린다.

**히어로/표지 규율**
표지 제목 2줄 이하, 부제 20단어 이하. 제목 블록이 화면 중턱에 떠 있지 않게.

**Eyebrow 개수 상한**
대문자 트래킹 마이크로 라벨은 `올림(슬라이드 수 / 3)` 이하.

**중복 CTA 금지**
같은 의도의 행동 유도가 두 개 있으면 하나로 합친다.

**카피 자가검수**
모든 문장을 다시 읽는다. 문법이 깨졌거나 지어낸 표현이 있으면 고친다.

### 4.A 조정해서 쓰는 것

**em dash 금지(§9.G)** — 원본은 전면 금지다. 한국어 슬라이드에서는 완화한다.
- 본문 문장부호로 쓰는 것은 허용
- **장식용으로 쓰는 것은 금지** — eyebrow, 인용 출처, 캡션 꼬리표, 제목 뒤 부연

**숫자 표기** — 원본에는 없는 규칙이다. 별도 숫자 표기 규약(원 단위 풀 콤마, 만/억/조 축약 금지 등)이 있으면 **그 규약이 상위**다. 그래프 축 라벨만 예외로 축약을 허용한다.

## 5. 존 경계 — 밀도보다 상위

밀도를 채우는 것과 존 경계를 지키는 것이 충돌하면 **경계가 이긴다**.

- 본문은 본문 박스 안에서만 산다. 위로 부제 영역, 아래로 푸터 여백을 침범하지 않는다
- "이 슬라이드는 본문이 좀 길다"는 침범 사유가 아니다. **슬라이드를 쪼갠다**
- 표지·섹션 구분·마무리 슬라이드는 프레임을 의도적으로 깨도 된다. 단 *깨는 것이 디자인 의도일 때만*

본문이 넘칠 때의 처리 순서:

1. 내용을 줄인다(문장 압축, 중복 제거)
2. 시각화로 바꾼다(표 → 차트, 목록 → 타일)
3. 슬라이드를 쪼갠다
4. **폰트를 줄이는 것은 마지막 수단이고, 규격 하한 아래로는 내리지 않는다**

## 6. HTML 프리뷰 → PPTX 변환 규약

### 6.A 원칙

**HTML은 디자인 확정용 프리뷰이고, 최종 산출물은 PPTX다.**

HTML 렌더 결과를 통째로 이미지로 구워 슬라이드 배경에 깔지 않는다. 텍스트가 죽어 수정이 불가능해지고, "차트 텍스트는 live text여야 한다"는 통상의 덱 규격을 위반한다.

**복합 방식이 기본이다.**

| 요소 | 처리 |
|---|---|
| 제목·부제·본문·표·차트 라벨·출처 | **live text**. python-pptx 텍스트박스로 재구성 |
| KPI 타일·카드·구분선 | **도형**. python-pptx 도형으로 재구성 |
| 복잡한 다이어그램·타임라인·폭포 차트 | SVG/PNG 이미지 허용 (별도 도표 스킬 경로 사용) |
| 로고 | 원본 PNG를 알파 보존해 그대로 삽입. 재가공 금지 |

### 6.B 캔버스 규격

HTML 프리뷰는 **1920 × 1080 px 고정 캔버스**로 그린다. 반응형으로 만들지 않는다.

```css
.slide {
  width: 1920px;
  height: 1080px;
  overflow: hidden;   /* 스크롤이 생기면 그 슬라이드는 넘친 것이다 */
}
```

### 6.C 144dpi 환산표

슬라이드 13.333″ × 7.5″ → 1920 × 1080 px 이므로 **1인치 = 144px**, **1pt = 2px**.

**길이**

| 인치 | px |
|---|---|
| 0.3″ | 43.2 |
| 0.4″ | 57.6 |
| 0.5″ | 72 |
| 1.0″ | 144 |
| 2.0″ | 288 |
| 5.5″ | 792 |

**폰트 (pt → px)**

| pt | px | | pt | px |
|---|---|---|---|---|
| 9 | 18 | | 20 | 40 |
| 10 | 20 | | 24 | 48 |
| 11 | 22 | | 32 | 64 |
| 12 | 24 | | 36 | 72 |
| 14 | 28 | | 40 | 80 |
| 16 | 32 | | 48 | 96 |
| 18 | 36 | | 56 | 112 |

**존 좌표 환산 (13.333″ × 7.5″ 규격 기준. 다른 규격이면 규격 값으로 다시 계산한다)**

| 존 | 인치 | px |
|---|---|---|

### 6.D 폰트 처리

- HTML 프리뷰의 `font-family` 첫 항목은 **렌더링 환경에 실제로 존재하는 폰트**여야 한다. 없는 폰트를 첫머리에 두면 한글이 네모(□)로 깨진다
- PPTX 내보내기 시 규격 서체를 파일에 임베드한다
- 프리뷰에서 예뻐 보였다는 이유로 폰트를 바꾸지 않는다(§2.A)

### 6.E 진행 순서

1. 슬라이드 모드 선언 + 원본 로드 + 규격 확인
2. 슬라이드별 내용 구조 확정(무엇을 시각화할지)
3. HTML 프리뷰 생성 → 사용자에게 보여주고 **승인 받기**
4. 승인 후 python-pptx로 재구성
5. §7 프리플라이트 실행
6. 최종 파일을 사용자 폴더에 저장하고 파일 카드로 제시
